# ADR-007: Username/password accounts with server-side sessions in SQLite

**Date:** 2026-11-07
**Status:** accepted

## Context

Folio had one built-in user (`'local'`): anyone who opened the page saw and
changed the same portfolio, and the landing page's "Log in" and "Get started"
buttons went straight to it. The final version needs login (UC5). Folio runs
locally, already stores everything in SQLite (ADR-002), and should stay free of
external services that a grader or peer reviewer would have to sign up for.
The brokerage tables were already keyed by a user id, so the data model was
ready for more than one user; holdings were not.

## Decision

- **Accounts are a username and password, stored in SQLite.** Passwords are
  hashed with scrypt (built into Node's `crypto`) with a random salt each, as
  `scrypt$<salt>$<hash>`, and compared in constant time. Usernames are unique
  in any case. The rules (3-32 characters; passwords 8-200 and not the
  username) are Domain functions in `src/accounts.js`.
- **Sessions are server-side.** Logging in creates a random 32-byte token,
  sent to the browser in a `folio_session` cookie (`HttpOnly`, `SameSite=Lax`,
  `Secure` when `APP_URL` is https, 7 days). The `sessions` table stores only
  the token's SHA-256 hash, so a copy of the database can't be used to log in.
  Logging out deletes the session.
- **The server is the gate.** `server.js` looks up the session on every
  request. Logged out, the portfolio page redirects to `/login.html?next=...`
  and every `/api/` route except `/api/auth/*` returns 401; the page sends a
  401 back to the login page too. Logged in, the user's id is passed to every
  Service call, and every data query filters by it, so one account can't read
  or change another's holdings even with a known holding id.
- **Each account has its own portfolio.** `holdings` gained a `user_id`
  column (a migration adds it to existing databases with the old default
  `'local'`). The first account ever created takes over everything owned by
  `'local'` (holdings and brokerage data), so upgrading loses nothing.
  Service and data functions default `userId` to `'local'`, so code and tests
  written for one user still work.
- **Slow down guessing.** Five failed logins for a username lock it for 15
  minutes. A wrong password and an unknown username get the same answer, and
  an unknown username still runs a hash, so neither the message nor the timing
  reveals which usernames exist.

Alternatives considered: a third-party login (Google, Auth0), which needs
accounts, keys and a public callback URL, too much for a local app; signed
JWT cookies with no sessions table, which can't be revoked on logout without
the table anyway; a passwords-only gate in front of a shared portfolio, which
would let every account see every other account's holdings; and an auth
library (Passport, express-session), which assumes Express, which Folio doesn't
use.

## Consequences

Login works with no new dependency or service, and each account's data stays
separate. Not covered, and worth doing before a real deployment: password
reset and changing a password (there's no email address to send a reset to),
a lockout that also limits by IP (today someone could lock another user out by
failing on purpose), cleaning up sessions when a user changes their password,
and HTTPS (the cookie is marked `Secure` only when `APP_URL` is https). The
free SnapTrade tier allows one connected user, so in practice only one account
can connect a brokerage.
